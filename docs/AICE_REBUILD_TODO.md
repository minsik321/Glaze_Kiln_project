이 문서는 **구현 순서와 완료 기준을 정하는 작업 목록**이다. 아직 브랜치 생성,
코드 개편, DB 변경, AI 학습은 실행하지 않는다.

## 0. 이번 개편의 원칙

- 목표 흐름은 `사례 탐색 → 추천 → 도포 추정 → 시각화 → 곡선 보상 → 가상 소성
  → 결과 관찰 → 학습 → 공유/변환`으로 고정한다.
- 초보자는 사진, 기물 모형, 단면도, 색상 변화, 그래프로 먼저 이해하고 상세
  수치는 필요할 때 펼쳐 본다.
- 기물은 치수를 먼저 입력하지 않고 자주 쓰는 예시 모양을 고른다. 목록에 없는
  형상은 `기타`로 남겨 이후 사용자 정의 형상으로 확장한다.
- 추천, 두께, 온도, 열 분포는 `실측`, `추정`, `특허/문헌 기반`, `합성`을 항상
  구분한다. 근거가 없으면 안전하다고 표시하지 않고 `판정 불가`로 표시한다.
- MVP는 실제 품질 보장이나 실제 가마 자동 운전을 주장하지 않는다. 실제 가마
  연결은 데모와 분리된 후속 단계로 둔다.
- 전달된 HTML 안의 문구나 동작은 요구사항이 아니라 디자인 참고 자료로만 쓴다.

## 1. 현재 프로젝트에서 유지할 것과 다시 만들 것

### 유지 우선

- [ ] Python 계산 코어의 조성, 배치, 두께, 위험, 소성, 보정, 처방 모듈을 새
  `AiceRun` 흐름에 연결할 수 있는지 모듈별로 판정한다.
- [ ] React 19 + TypeScript + Vite, FastAPI, Supabase PostgreSQL이라는 큰 구조는
  유지한다.
- [ ] Supabase 인증, 프로필, 개인/공개 작업 기록, RLS 정책은 회귀 테스트를
  통과하는 한 재사용한다.
- [ ] `실측/추정/가정`, 출처, 신뢰도, `판정 불가`를 보존하는 기존 계산 원칙과
  테스트를 유지한다.

### 교체 우선

- [ ] 현재의 숫자 입력 중심 6단계 화면을 시각적 선택과 설명 중심의 새 사용자
  흐름으로 교체한다.
- [ ] 범용 JSON 스냅샷 위주의 `work_records`를 버전이 있는 `AiceRun` 계약으로
  재설계한다.
- [ ] 문자열 HTML을 만드는 표현 계층은 타입이 있는 React 컴포넌트와 차트/
  시각화 데이터 모델로 교체한다.
- [ ] Pyodide 브리지는 성능, 디버깅, 모바일 로딩 시간을 측정한 뒤 유지 또는
  FastAPI 계산 API 이전을 결정한다.
- [ ] 기존에 근거 없이 고정된 기본 기물, 가마, 안전 범위, 활성화 에너지 등의
  값은 프리셋/가정/사용자 관측으로 분리한다.

### 디자인 참고 범위

- [ ] HTML의 차분한 청회색 강조색, 밝은 중성 배경, 가는 경계선, 설계도형 코너
  표시, 한 화면 한 작업, 하단 주요 행동 버튼을 디자인 토큰으로 정리한다.
- [ ] 390px 모바일 1열 구성을 기본으로 삼되 태블릿/데스크톱에서는 시각화와
  설명을 나란히 볼 수 있는 반응형 레이아웃을 만든다.
- [ ] HTML의 작은 글자와 촘촘한 숫자 입력은 그대로 복제하지 않는다. 터치 영역,
  대비, 본문 크기, 색각 이상 대응, 키보드 탐색 기준을 먼저 확정한다.

## 2. 실행 순서

### Phase 0 — 새 브랜치와 기준선 격리

- [ ] GitHub 원격 최신 상태를 확인하고 현재 작업 및 미추적 문서를 보존한다.
- [ ] 현재 브랜치에서 새 작업 브랜치 `aice-direction-plan`을 만든다.
  브랜치 생성 시점에는 기능 코드를 바꾸지 않는다.
- [ ] 현 버전을 태그 또는 기준 커밋으로 남겨 언제든 기존 앱과 비교할 수 있게
  한다.
- [ ] 현행 전체 테스트, 빌드, 주요 모바일 화면 캡처, DB 스키마를 기준선으로
  기록한다.
- [ ] 새 브랜치에서 사용할 환경 변수, 로컬 Supabase, 샘플 데이터 구성을 문서화한다.

완료 기준: 기존 브랜치와 완전히 분리된 새 브랜치에서 현행 앱이 동일하게 실행되고,
기준선 테스트 결과와 되돌아갈 커밋이 기록되어 있다.

### Phase 1 — 제품 범위와 사용자 흐름 확정

- [ ] MVP 사용자를 `유약/가마 비전문가가 시각적 안내를 받으며 한 번의 가상
  실험을 완료하는 경우`로 정의한다.
- [ ] 핵심 흐름을 다음 화면으로 확정하고 저해상도 와이어프레임을 만든다.
  1. 홈/지난 실행
  2. 원하는 결과 선택
  3. 사진이 있는 레시피 후보 비교
  4. 기물 모양 및 소지 선택
  5. 도포 기록과 유약 단면 확인
  6. 가마 적재·센서 배치
  7. 보정 소성곡선과 PID 계획 확인
  8. 가상 소성 진행
  9. 결과 평가와 다음 제안
- [ ] 화면 기본층에는 선택 카드, 그림, 상태 문장만 두고 수식·원시값·출처는
  `상세 보기`에 둔다.
- [ ] 모든 추천 화면에 `왜 이 후보인지`, `무엇이 가정인지`, `다음 행동은
  무엇인지`를 짧은 문장으로 제공한다.
- [ ] 실제 가마 제어처럼 오해할 수 있는 버튼과 문구를 제거하고 데모/시뮬레이션
  배지를 고정 표시한다.

완료 기준: 숫자를 직접 입력하지 않아도 샘플 실행 하나를 끝낼 수 있는 클릭형
프로토타입과 화면별 정보 우선순위가 승인되어 있다.

### Phase 2 — 디자인 시스템과 반응형 앱 뼈대

- [ ] HTML에서 색상, 간격, 타이포그래피, 경계선, 그림자, 아이콘 규칙을 추출해
  CSS 변수와 React 공통 컴포넌트로 만든다.
- [ ] `AppShell`, 상단 진행 상태, 하단 내비게이션, 카드, 선택 칩, 상태 배지,
  설명 패널, 상세 정보 서랍, 경고/판정 불가 컴포넌트를 만든다.
- [ ] 모바일 우선으로 구현하고 390px, 768px, 1280px에서 레이아웃을 검증한다.
- [ ] 색상에만 의존하지 않는 범례, 충분한 대비, 44px 이상 터치 목표, 스크린리더
  이름, 키보드 포커스, 모션 감소 설정을 적용한다.
- [ ] 초기 화면에서 Pyodide 로딩이 작업을 막지 않도록 앱 셸과 선택 화면을 먼저
  표시하고 계산 엔진은 필요한 시점에 준비한다.

완료 기준: 실제 데이터 없이도 모든 핵심 화면의 빈 상태, 로딩, 오류, 판정 불가,
완료 상태를 재사용 컴포넌트로 확인할 수 있다.

### Phase 3 — `AiceRun` 데이터 계약과 DB 마이그레이션

- [ ] 프론트엔드, Python, FastAPI, DB가 공유할 `AiceRun` 스키마를 먼저 정의한다.
- [ ] 최소 하위 모델을 분리한다: 목표, 레시피/사진, 기물/소지, 도포 측정,
  두께 추정, 적재/센서, 기준·후보·선택 곡선, PID 실행, 결과 평가, 출처/동의,
  모델 버전.
- [ ] 모든 값에 단위와 `source_type`(`observed`, `patent_example`,
  `patent_range`, `literature`, `inferred`, `synthetic`)을 기록할 수 있게 한다.
- [ ] 범용 `payload`는 호환용으로 남기되 검색이 필요한 필드는 정규화한다.
- [ ] 레시피 사진과 결과 사진용 Supabase Storage 버킷, 메타데이터, 소유권,
  공개 범위, 삭제 정책을 설계한다.
- [ ] 스키마 버전 업/다운 변환과 기존 `work_records` 읽기 전용 호환 또는 이전
  스크립트를 설계한다.
- [ ] RLS로 개인 실행, 동의된 공개 실행, 사진 파일, 개인 보정치를 분리한다.

완료 기준: 샘플 실행 하나가 프론트엔드 타입, API 검증, DB 저장, 다시 불러오기를
왕복하며 출처와 버전을 잃지 않는다.

### Phase 4 — 선택 중심의 목표·기물·레시피 경험

- [ ] 목표는 광택, 투명도, 색상, 질감을 사진/스와치 카드로 선택하게 하고 고급
  수치 조절은 보조 기능으로 둔다.
- [ ] 기물 기본 카탈로그를 `사발`, `접시`, `컵/머그`, `원통 화병`, `병`,
  `타일/평판`, `기타`로 만든다.
- [ ] 각 기물 카드에 실루엣, 대표 크기 범주, 안/밖 시유 여부를 표시한다.
- [ ] `기타`는 MVP에서 간단한 설명과 사진 또는 실루엣 선택만 받고, 정밀 치수/
  사용자 메시 업로드는 후속 기능으로 둔다.
- [ ] 선택한 기물 프리셋을 면적·두께 분포 계산에 쓰되 `대표 형상에 근거한 추정`
  임을 표시한다.
- [ ] 레시피 후보 카드에 결과 사진, 목표와의 유사 이유, 소성 범위, 출처, 실제/
  합성 여부, 데이터 수, 불확실성, 위험 요약을 표시한다.
- [ ] 사진이 없으면 색상/질감 플레이스홀더를 쓰고 예상 실물 사진처럼 보이는
  합성 이미지를 자동 표시하지 않는다.
- [ ] 후보 비교는 최대 3개를 이미지와 핵심 차이 중심으로 제공하고 배합 퍼센트와
  화학 상세는 펼쳐 보기로 둔다.

완료 기준: 사용자가 숫자 계산 없이 목표, 레시피, 기물 선택을 완료하고 선택 근거와
데이터 성격을 이해할 수 있다.

### Phase 5 — 유약 두께 종단면 시각화

- [ ] 기본 기물별 정규화된 2D 종단면 형상과 표면 구간 좌표를 자산으로 만든다.
- [ ] 선택 기물에 유약층을 실제보다 과장해 그리며 화면에 `두께 표현은 이해를
  위해 과장됨`을 상시 표시한다.
- [ ] 유약층을 얇음/목표 근처/두꺼움/판정 불가 색으로 표시하고 색 외에 패턴과
  레이블도 함께 사용한다.
- [ ] 전체 무게만 있는 경우 평균 추정 두께만 확정적으로 보이고 위치별 분포는
  `형상 기반 가상 분포`와 불확실 범위로 표시한다.
- [ ] 구간 측정, 사진 분석, 스캔 등 위치 근거가 있을 때만 위치별 값을 강화한다.
- [ ] 굽, 모서리, 안쪽 바닥 등 위험 지점을 단면도 위 콜아웃으로 설명한다.
- [ ] 입력 변화가 단면, 위험 문장, 소성곡선 후보에 연쇄 반영되는 상태 연결을
  구현한다.

완료 기준: 비전문가 테스트에서 사용자가 숫자표 없이도 어느 부분이 상대적으로
두껍고 왜 위험한지 설명할 수 있다.

### Phase 6 — 가마 적재·센서·열 변화 종단면 시뮬레이터

- [ ] 전기가마 세로 종단면 모델을 만들고 선반 층, 열선, 문/뚜껑, 배기,
  단열벽을 구분한다.
- [ ] 선택한 기물 형상이 각 선반에 실제 적재된 것처럼 보이도록 배치한다.
- [ ] 센서 수와 위치 프리셋을 `기본 1개`, `상·중·하 3개`, `다점 측정`으로
  제공하고 사용자가 단면도에서 위치를 조정할 수 있게 한다.
- [ ] 센서마다 측정 대상, 사각지대, 대표성 한계를 설명하고 필요한 센서 수는
  가마 크기·적재 형태에 따른 추천으로 제시한다.
- [ ] 시간 재생, 일시정지, 구간 이동을 제공하고 온도장은 냉색→온색 열지도로,
  대류는 느린 흐름선/입자 애니메이션으로 표현한다.
- [ ] 대류 애니메이션은 정량 CFD 결과로 오해되지 않도록 `설명용 근사`로
  표시한다. MVP 물리 모델과 시각 효과를 데이터 계층에서 분리한다.
- [ ] 센서 온도, 기물 추정온도, 층별 편차, 히터 출력을 같은 시간축으로 연결한다.
- [ ] 센서 고장, 편향, 과열, 층간 편차가 생기면 가마 그림의 해당 위치와 경고
  타임라인을 동시에 강조한다.

완료 기준: 같은 적재에서 센서 위치/개수를 바꾸면 관측 가능한 온도와 불확실성이
달라지고, 테스트로 그 연결을 재현할 수 있다.

### Phase 7 — 곡선 보상과 PID 설명 화면

- [ ] `기준 계획`, `두께 반영 수정 계획`, `시뮬레이션 실제`, `다음 실행 제안`을
  한 그래프에서 켜고 끌 수 있게 한다.
- [ ] 곡선 변경 구간에 `왜 바뀌었는지`를 직접 주석으로 표시한다.
- [ ] PID 화면은 계획값/센서값/기물 추정값 그래프, 추종오차, 히터 출력, 경보를
  시간축으로 동기화한다.
- [ ] P/I/D 수치 입력을 첫 화면에 노출하지 않고 `빠른 반응`, `안정 우선`,
  `균형` 같은 설명형 프리셋과 예상 효과를 먼저 보여준다.
- [ ] 고급 상세에서만 게인, 포화, anti-windup, 샘플링 주기, 제약조건과 원시
  로그를 제공한다.
- [ ] 초기 계획과 수정 계획의 최고온도, 유지시간, 냉각, 시간/에너지 차이를
  그래프 아래 자연어로 요약한다.
- [ ] 사용자가 승인한 후보만 가상 제어기에 전달하고 모든 변경 이유와 버전을
  `AiceRun`에 기록한다.

완료 기준: 사용자가 그래프만 보고 계획이 언제, 어느 방향으로, 왜 수정됐는지와
실제 추종이 어땠는지 설명할 수 있다.

### Phase 8 — 특허·문헌 기반 AI MVP

- [ ] 방향성 문서의 네 특허와 참고문헌을 데이터 카드로 만들고 공보번호,
  문단/실시예, 원 조건, 단위변환, 해석, 적용 한계를 기록한다.
- [ ] 특허의 사진·도면을 앱 자산이나 학습 데이터로 복제하지 않고 허용된 수치,
  관계, 방법만 구조화한다.
- [ ] 1차 추천은 `출처 있는 규칙 + 기존 레시피 검색 + 제약 기반 랭킹`으로
  구현한다.
- [ ] 소규모 검색용 RAG와 수치 예측 모델을 별도 서비스/평가 항목으로 분리한다.
- [ ] 합성 데이터 생성기는 추정 모델과 다른 구조와 외란을 사용해 자기 답을
  그대로 학습하는 오류를 막는다.
- [ ] 학습 필요성 판단 게이트를 둔다.
  - 규칙/검색 baseline보다 개선할 명확한 목표와 평가셋이 있는가?
  - 사용 권리와 `source_type`이 확인된 표본이 충분한가?
  - train/validation/test가 실행 또는 출처 단위로 분리되는가?
  - 범위 밖 입력과 불확실성을 감지할 수 있는가?
- [ ] 게이트를 통과하지 못하면 학습 모델을 제품 경로에 넣지 않고 규칙/RAG
  MVP로 완료한다.
- [ ] 게이트를 통과하면 먼저 단순 baseline을 학습하고, 정확도뿐 아니라 보정
  오차, 범위 밖 실패, 데이터 누수, 개인/공통 편향을 평가한다.
- [ ] 검증을 통과한 모델만 버전, 데이터셋 버전, 성능표, 롤백 경로와 함께
  제한된 후보 점수에 사용한다.
- [ ] 개인화는 사용자별 모델 재학습이 아니라 개인 기록 검색과 가마/소지별
  보정계수부터 시작한다.

완료 기준: 같은 입력과 모델 버전에서 추천을 재현할 수 있고, 각 결과가 규칙,
RAG, 학습 모델 중 어디서 왔는지와 한계를 사용자가 확인할 수 있다.

### Phase 9 — 결과 관찰, 피드백, 공유

- [ ] 소성 후 사진 촬영 가이드에 표준 조명, 배경, 거리, 색상 기준표를 포함한다.
- [ ] 결과 평가는 색상, 광택, 질감, 투명도, 결함을 사진과 쉬운 선택지로 받고
  상세 수치는 선택 입력으로 둔다.
- [ ] 목표/결과 사진을 나란히 비교하고 차이를 다음 레시피·곡선 제안과 연결한다.
- [ ] 개인 보정과 공통 모델 개선 후보를 분리하고 자동으로 공통 모델에 반영하지
  않는다.
- [ ] 공개 전 사진 권리, 개인정보, 위치정보, 동의, 철회, 익명화 상태를 확인한다.
- [ ] 다른 사용자의 곡선은 그대로 복사하지 않고 내 가마·적재 조건으로 변환한
  후보를 다시 시뮬레이션한다.
- [ ] 기존 기록 목록/상세/페이지네이션과 새 `AiceRun` 복원 기능을 완성한다.

완료 기준: 결과 피드백 하나가 다음 추천 또는 개인 보정에 미치는 영향을 기록에서
추적할 수 있고, 공유 철회 후 외부 조회가 차단된다.

### Phase 10 — 검증, 성능, 로컬 실행 완성

- [ ] Python 계산 단위 테스트와 문서 수치 회귀 테스트를 유지한다.
- [ ] 프론트엔드 컴포넌트, 상태 전이, 그래프 범례, 접근성, 오류/판정 불가 상태를
  자동 테스트한다.
- [ ] `목표 → 사진 레시피 → 기물 → 유약 단면 → 센서 배치 → 곡선 보정 →
  가상 소성 → 결과 저장` 전체 E2E를 만든다.
- [ ] 입력 하나를 바꾸면 두께, 위험, 후보곡선, 가마 시각화, 기록이 모두 같은
  실행 버전으로 바뀌는 통합 테스트를 만든다.
- [ ] 합성/특허 기반 값을 실측처럼 표시하지 않는 회귀 테스트를 만든다.
- [ ] 모바일 초기 표시, 계산 엔진 로드, 그래프/애니메이션 프레임 성능과 저사양
  기기 대체 표현을 점검한다.
- [ ] 로컬 Supabase 마이그레이션, 백업/복구, 스토리지 정책, FastAPI와 프론트엔드
  로컬 실행 절차를 정리한다.
- [ ] 두 계정으로 가입, 개인 저장, 공개, 타인 조회, 철회, 삭제, 복원을 수동
  검증한다.
- [ ] 실제 가마 연결 기능은 이번 로컬 MVP에 포함하지 않는다.

완료 기준: 자동 테스트·빌드·접근성 검사와 핵심 수동 시나리오가 통과하고, 기존
버전으로 되돌릴 수 있으며 데이터 백업/복구 절차가 검증되어 있다.

## 3. 우선순위 백로그

### P0 — MVP 필수

- [ ] Phase 0 브랜치 격리와 기준선
- [ ] Phase 1 사용자 흐름 및 안전 문구
- [ ] Phase 2 공통 UI와 반응형 앱 셸
- [ ] Phase 3 `AiceRun` 계약
- [ ] 사진이 있는 레시피 후보와 기물 예시 선택
- [ ] 과장 표시된 유약 두께 종단면
- [ ] 층별 기물·센서가 보이는 가마 종단면과 설명용 열 변화
- [ ] 기준/수정/실제 곡선 및 PID 계획 비교
- [ ] 규칙·검색 기반 AI MVP와 출처 표시
- [ ] 전체 흐름 저장/복원과 E2E

### P1 — MVP 품질

- [ ] 결과 사진 촬영/평가
- [ ] 개인 가마·소지 보정
- [ ] 센서 고장/편향/층간 편차 시나리오
- [ ] 공개 실행의 내 가마 조건 변환
- [ ] 접근성·성능·오프라인/느린 연결 대응

### P2 — 데이터가 확보된 뒤

- [ ] 사용 허가가 확인된 데이터셋 구축
- [ ] 수치 예측 baseline 학습과 독립 평가
- [ ] 사용자 정의 `기타` 형상 편집 또는 메시 업로드
- [ ] 더 정교한 열 모델/대류 표현 검증
- [ ] 공통 모델 갱신 심사, 적용, 롤백 자동화

### 보류 — 별도 안전 프로젝트

- [ ] 실제 센서 및 가마 컨트롤러 연결
- [ ] 독립 과열 차단, 통신 실패 안전상태, 사용자 승인, 감사 로그
- [ ] 실제 가마 연결이 필요해질 경우의 별도 안전 검토

## 4. 개편 완료 정의

- [ ] 비전문가가 기본 흐름에서 수식이나 대량의 숫자를 보지 않고 한 번의 가상
  소성을 완료한다.
- [ ] 레시피는 사진과 근거로, 기물은 예시 모양으로, 도포는 과장된 종단면으로,
  소성은 가마 종단면과 열 흐름으로 이해할 수 있다.
- [ ] 센서 위치/개수와 기물 적재가 관측 온도와 불확실성에 실제로 연결된다.
- [ ] 초기 계획, 수정 계획, 시뮬레이션 실제, 다음 계획이 한 시간축에서 구분된다.
- [ ] 모든 추천과 시각화에서 실측·추정·특허/문헌·합성 여부와 신뢰도를 확인할
  수 있다.
- [ ] 동일 입력, 데이터 버전, 모델 버전으로 결과가 재현되고 이전 버전으로
  롤백할 수 있다.
- [ ] 기존 인증·개인 기록·공개 기록의 보안 경계가 유지된다.
- [ ] 실제 품질 보장 또는 실제 가마 자동 제어로 오해될 표현이 없다.
