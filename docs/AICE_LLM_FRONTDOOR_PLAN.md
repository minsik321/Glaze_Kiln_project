# AICE — LLM 통합 프런트도어 플랜 (v9)

브랜치: `feature/llm-frontdoor-v9`
기준 문서: `kiln-plan-v7.md`, `CLAUDE.md`(루트·모듈별), `AICE_DIRECTION_PLAN.md`,
`AICE_USER_FLOW.md`, `AICE_REBUILD_TODO.md`, `DECISIONS.md`

## 0 · 문서의 위치와 우선순위

이 문서는 "LLM을 맨 앞에 붙이는" 신규 요구사항(채팅형 입구, RAG·Prediction·
Optimization 3계층 AI, 화면 단순화)을 반영한 최신 방향성이다.

**충돌 시 이 문서가 우선한다.** 사용자가 명시적으로 "기존 기획서보다 지금
새로 기획하는 기획서가 최우선"이라고 확인했다(2026-09-17). 물리 계산 코어
(두께·위험·열일·냉각), provenance 체계, "판정 불가"·"조용한 기본값 금지"
원칙, 특허·문헌 인용 체계는 신규 요구사항과 충돌하지 않으므로 그대로
유지·재사용한다. 어디가 유지되고 어디가 갈아엎이는지는 2절·7절에 명시한다.

## 1 · 시스템 정의 (확정)

> 초기에는 도예 지식과 기존 실험 데이터를 검색하여 기준 소성 조건을 산출하고,
> 이후 사용자의 기물/시유량/가마/소성 결과 데이터를 반복적으로 축적하여
> 사용자별 공정 모델을 보정한다. 목표 결과와 실제 결과 간 오차를 기반으로
> 다음 소성 조건을 조정함으로써 반복 소성의 결과 편차를 감소시키는
> 폐루프(closed-loop) 유약/소성 최적화 시스템.

이 정의는 `AICE_DIRECTION_PLAN.md` 1절의 정의를 대체한다(구조는 크게 다르지
않으나 "폐루프"라는 단어와 "사용자별 공정 모델 보정"이 이번 정의의 핵심이다).

## 2 · 기존 원칙과의 충돌과 해소

### 2-1. "AI를 판단 주체로 쓰지 않는다" — 스코프를 좁혀 재정의

`src/kiln/webapp/CLAUDE.md`와 `src/kiln/search/CLAUDE.md`는 "이 경계에도
모델 호출이 없다", "난수·학습 모델·LLM이 개입하지 않는다"를 못박아 두었다.
신규 요구(LLM 채팅 입구, RAG 추천, Prediction Model, Optimization Model)는
이 문구와 정면으로 부딪힌다. 사용자 확인에 따라 다음과 같이 원칙을
**전면 폐기가 아니라 스코프 분리**로 재정의한다.

| 스코프 | 범위 | AI/LLM 허용 여부 |
|---|---|---|
| **A · 물리 판정 코어** | 두께 총량제약(`kiln.thickness`), 위험 판정(`kiln.risk`), 열일 적분·냉각 상한(`kiln.firing`) | **금지 유지.** 실측값과 결정론적 수식만. 안전·재현성의 최종 보루이므로 신규 요구와 무관하게 그대로 둔다 |
| **B · 추천·예측·개인화 계층 (신규)** | 채팅 입구, 레시피 추천(RAG), 결과/소성조건 예측(Prediction), 개인화 보정(Optimization) | **허용.** 단 모든 출력에 `source_type`(§6 taxonomy 재사용)을 반드시 붙이고 "결과를 보장하지 않는다"는 태도를 유지 |

02절이 GlazyBench를 분석하며 내린 진단 — "조성만으로는 결과를 예측할 수
없다, 입력에 소성 과정이 없기 때문이다" — 은 폐기하지 않는다. 오히려 이번
Prediction Model이 조성 **단독**이 아니라 두께·소성이력·가마·개인 이력을
전부 입력으로 받는다는 점에서, 이 진단이 요구하는 해법 쪽으로 가는 것이라고
읽는다. "조성만으로 예측 금지"가 "전체 조건 없이 예측 금지"로 스코프가
좁혀지는 것이지, 진단 자체가 뒤집히는 것이 아니다.

### 2-2. 설명형 UI 원칙 — 상시 노출 문구·이름 붙은 프리셋 제거

`AICE_USER_FLOW.md`는 모든 화면에 "왜 / 가정 / 다음 행동" 3줄 문구를
필수로 못박고, 화면 7에 "빠른 반응 / 균형 / 안정 우선"처럼 이름 붙은 제어
프리셋을 둔다. 사용자는 이 설명형 패턴 자체를 걷어내고 이미지·짧은 문구만
보고 넘어가는 사용성을 요구했다.

**결정**: 상시 노출 3줄 문구를 기본층에서 제거한다. provenance 배지(예:
"관측" / "AI 추정" / "합성")는 최소 아이콘·라벨 형태로 유지하되, 문장형
설명(왜·가정·다음행동)은 전부 상세보기로 내리거나 삭제한다. 이름 붙은
제어 프리셋(빠른 반응/균형/안정 우선)은 삭제하고, 소성곡선 조정은 AI가 낸
계획 하나를 보여주고 "이대로 진행 / 다시 추천" 두 선택지로 단순화한다.

## 4 · AI 아키텍처 — 역할 분리 (11-c)

기존 `AICE_DIRECTION_PLAN.md` 9절이 이미 4계층(Patent/Literature RAG,
Rule/Simulation Model, Experimental Predictor, Personal Calibration)으로
쪼개 두었다. 사용자가 이번에 요청한 3계층 이름에 맞춰 아래처럼 대응·통합한다.

| 사용자 용어 | 역할 | 대응하는 기존 자산 | 신규 작업 |
|---|---|---|---|
| **RAG** | 자연어 기반 레시피 탐색 | 9절 "Patent/Literature RAG", `kiln.search.Prior` | aimlapi.com 텍스트 모델 실배선, 사용자 축적 레시피를 코퍼스에 추가, 원료 화학·성분 상관관계 자료 인덱싱 |
| **Prediction Model** | 입력조건 → 결과·소성조건 예측 | 9절 "Rule/Simulation Model" + "Experimental Predictor" 통합 | §5 변수 세트를 입력으로 받는 예측 함수 신설. 출력에 `source_type=inferred`/`synthetic` 필수 |
| **Optimization Model** | 목표-실제 오차 누적 → 다음 소성조건 개인화 보정 | `kiln.calibration`(10-2절), 9절 "Personal Calibration" | 사용자별 계수 테이블과 위 Prediction Model을 잇는 갱신 루프 연결 |

물리 판정 코어(§2-1 스코프 A)는 이 세 계층 중 어디에도 속하지 않는다.
Prediction Model이 "예상 두께 0.9mm"를 내도, 실제 위험 판정은 여전히
저울 실측값과 `kiln.risk`의 결정론적 규칙이 한다 — AI 출력은 계획을 세우는
데 쓰이고, 안전 여부의 최종 판정에는 쓰이지 않는다.

## 5 · 11-a/b 기술 보완 반영

### 5-a. 유약 두께 계산 — 단위면적당 도포량(g/m²) 승격

`kiln.thickness`는 이미 저울 두 번(시유 전/후 무게차)과 형태 표면적으로
총량 제약을 걸어 두께를 낸다 — 사실상 "무게차 ÷ 면적"인 단위면적당 도포량이
1차 산출값이고, mm 환산은 `ρ_dry`(문헌 추정 · 미확정)를 곱한 2차 파생값이다
(`kiln.calibration`의 `areal_slope` C가 정확히 이 값이다). 물리량 자체는
이미 사용자가 요청한 방식과 같다. 이번에 할 일은 **표시 우선순위를 뒤집는
것**이다.

- `ThicknessProfile`에 `areal_density_g_m2` 필드를 1급으로 노출한다(현재는
  `kiln.calibration` 내부에서만 계산됨).
- 화면·API 응답에서 g/m²을 주 수치로, mm을 "추정값(ρ_dry 가정 기반)"
  라벨을 붙인 보조 수치로 표시한다.
- 두께(mm) 자체를 폐기하지 않는다 — 07절 위험 판정(흘러내림·미용융 임계값)이
  mm 단위이므로 두 단위를 함께 들고 간다.

## 6 · 인용 자료 — 별도 문서로 분리

사용자 지시에 따라 개별 화면·컴포넌트에 인용을 달지 않는다. 전부
[`AICE_CITATIONS.md`](AICE_CITATIONS.md) 한 곳에 모은다. 특허는 인용 가능성이
불확실하므로(`AICE_DIRECTION_PLAN.md` 7절이 이미 특허마다 "변리사 재확인"
caveat을 달아 두었다) 이번에 새로 채택하는 계산·설계 근거는 **학술 논문을
1순위**로 삼는다. 기존 특허 인용은 caveat과 함께 유지하되 신뢰 근거의
우선순위에서 논문 뒤로 내린다.

## 8 · 외부 API 연동

- **확정(2026-09-17, 3차)**: 사용자가 [aimlapi.com](https://aimlapi.com)에서
  API 키를 이미 발급받았고, 텍스트(RAG 레시피 추천)와 이미지(레시피 예상
  이미지) 생성을 이 키 하나로 통합해서 쓰기로 확정했다. Anthropic API 키·
  Gemini API 키를 따로 발급받는 원안(§2-1 이하 v9 초안, Phase 0 최초 커밋)은
  이 결정으로 대체한다 — Anthropic·Gemini를 직접 호출하지 않고, aimlapi.com이
  두 제공사를 포함한 여러 모델을 중계하는 단일 게이트웨이 역할을 한다.
  - 텍스트: `https://api.aimlapi.com/v1/chat/completions` (OpenAI 호환 포맷),
    `Authorization: Bearer <AIMLAPI_API_KEY>` 헤더, `model` 필드로 공급사·모델을
    지정(예: `anthropic/claude-sonnet-4.6`).
  - 이미지: `https://api.aimlapi.com/v1/images/generations`, 같은 인증 방식,
    `model` 필드로 이미지 모델 지정. **기본값은 `google/nano-banana`**
    (Google의 텍스트+이미지 프롬프트 겸용 네이티브 이미지 모델, 장당 약
    $0.05~0.065) — 화면 1이 자연어 스타일 설명과 함께 **선택적으로 색상
    사진을 입력받아 그 색을 반영한 예상 이미지를 내야 하는데, 이 모델은
    이미지를 프롬프트에 함께 넣는 image-conditioned 생성을 지원해서 색상
    참고 사진을 실제로 반영할 수 있다(Flux 계열 상당수는 텍스트 전용이라
    이 요구를 못 채운다). 후보 5장 생성 시 세션당 약 $0.3 내외로 데모
    단계 비용은 크지 않다. 색상 사진 없이 텍스트만으로 충분한 경우로
    범위를 좁히면 `flux/schnell`(약 $0.0039/MP, 1024×1024 기준 장당 약
    $0.004)로 비용을 더 낮출 수 있다. 정확한 모델 ID·가격은 자주 바뀌므로
    구현 시점에 [모델 데이터베이스](https://docs.aimlapi.com/api-references/model-database)
    로 재확인한다.
  - 키는 `backend/.env`에만 둔다(`backend/.env.example` 참고). 루트 `.env`는
    Vite가 읽어 프런트엔드 번들에 들어갈 수 있으므로 여기 두지 않는다 —
    RAG 호출·이미지 생성은 전부 백엔드(`kiln.aice` 확장 또는 신규 `kiln.llm`
    모듈)를 거쳐 서버 사이드에서만 aimlapi.com에 요청한다.
  - aimlapi.com은 Anthropic·Google의 공식 API가 아니라 제3자 중계 게이트웨이다.
    청구·요청 처리·모델 가용성이 그 회사 정책을 따르며 Anthropic·Google이
    보증하지 않는다는 점을 리스크로 남겨 둔다(§9).
- **이전 결정(2026-09-17, 2차, 참고용으로 남김)**: "Claude Pro 계정으로
  fetch"는 상용화가 아니라 데모 버전 용도였고, 개인 구독 세션을 자동화로
  흉내 내는 방식은 이용약관상 허용되지 않으므로 Anthropic API 키를 쓰기로
  했었다. 3차 결정(aimlapi.com 단일 키)이 이를 대체하지만, "개인 구독 세션
  자동화는 안 된다"는 원칙 자체는 그대로 유효하다 — aimlapi.com도 정식
  발급된 API 키로 호출하는 것이지 누군가의 구독 세션을 흉내 내는 것이
  아니다.

## 9 · 남는 리스크

- `kiln-plan-v7.md` 부록 C·D의 특허 방어 논리("계수 값을 기재하지 않는다")와
  신규 Prediction/Optimization Model이 예측값(색·소성조건 등 구체적인 값)을
  실제로 화면에 내놓는 것 사이의 긴장은 이번 문서로 완전히 해소되지 않았다.
  이번 결정은 사용자의 명시적 우선순위 지정에 따른 것이며, 공개·출원 전에는
  변리사 재검토가 필요하다(`AICE_DIRECTION_PLAN.md` 10절 원칙 유지).
  **갱신(Phase 3·5 구현 후, 2026-09-17)** — 변리사 재검토용으로 긴장의
  범위를 좁혀 둔다. 실제 구현된 두 모델이 내놓는 값은 서로 성격이 다르다:
  - `app/react/aice/predictionModel.ts`(Prediction Model 초안)가 화면에
    내놓는 것은 소성곡선 유지구간 보정값(`holdDeltaC`, 예: "-3°C") 하나뿐
    이다. 이 값은 부록 C 표의 물리 계수(k1·k2·E·ρ_dry 등, "값 기재 금지"
    대상)를 계산하거나 노출하지 않는다 — 입력(기물 크기·레시피 소성범위·
    이전 실행 횟수)에서 곧바로 파생된 UX 표시값이고, source_type도 항상
    `synthetic`/`inferred`다. 즉 이 모델은 부록 C의 금지 대상과 직접
    충돌하지 않는다.
  - `src/kiln/calibration/`(Optimization Model, Phase 5)은 실제로 부록 C의
    `k1`·`rho_dry`를 다루지만, 프런트엔드로 그 값을 내보내는 배선은 아직
    없다(Phase 5 완료 메모 참고 — 의도적으로 Python 쪽에만 남겨둠). 값이
    화면에 나타나지 않는 한 "기재 금지" 원칙과 충돌할 여지도 없다.
  - 남은 긴장: Prediction Model의 `holdDeltaC`가 "예측"이라는 이름으로
    특허 청구항의 실시예(embodiment)처럼 읽힐 위험은 여전히 변리사 판단
    사항이다 — 이 문서는 그 판단을 대신하지 않는다.
- Prediction Model의 학습/추론 데이터가 초기에는 대부분 `synthetic`이라는
  점은 `AICE_DIRECTION_PLAN.md` P3 단계와 동일하게 유지된다 — 실제 정확도는
  주장하지 않는다.
- **aimlapi.com 단일 게이트웨이 의존(§8, 신규)**: 이 서비스는 Anthropic·
  Google의 공식 API가 아니라 제3자 중계상이다. 모델 가용성·응답 포맷·가격이
  예고 없이 바뀔 수 있고, 장애 시 대체 경로가 없다. 데모 단계라 리스크를
  감수하기로 했지만, 실사용 단계로 넘어가면 (a) 공식 Anthropic/Google API로
  직접 전환하거나 (b) 클라이언트 코드를 provider-agnostic하게(OpenAI 호환
  포맷 유지) 짜 두어 전환 비용을 낮추는 것을 재검토한다.
